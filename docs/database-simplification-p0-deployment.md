2. Once drained, suspend Studio writers, replication/background capture and peer delivery on all three hosts through their normal service controls. Include the complete scientific Database directory and content-addressed structure files; authentication/ownership/project databases and settings; Results and original source/workdirs (including external targets); application configuration and service/environment definitions; and the complete cluster state. ### Downgrade and re-upgrade procedure

1. Close admission and dispatch on **all three** workstations, drain or safely retain all work, and stop peer delivery and background capture through the existing service controls. Before switching any code, take a fresh consistent per-host backup of the full scientific Database, structure files, Results/source files, service configuration and cluster state. The cluster copy must include `replication.sqlite3` with records, conflicts, cursors, epochs and node identity, plus the database's WAL/SHM when using a filesystem snapshot. Keep each host's Database and replication catalog paired; never substitute another host's copy.
2. Keep each current `molecular_library.sqlite3` and `replication.sqlite3` intact. Do not delete, translate, rewrite or move `complex_review_annotation` rows, conflict records or cursors; do not restore a pre-upgrade catalog or reset an epoch. The old application may open the post-upgrade Database, but it cannot safely exchange shortlist events. Keep peer sync and background capture disabled on every old-version host, and do not create or edit shortlist annotations while rolled back.
3. Point all three workstations to the pinned previous code/environment and their own current Database/catalog copies. Start only the services needed for local operation, with peer delivery still disabled. Verify runtime provenance and that the new annotation rows, original Evaluations and replication events remain present. Do not run the old `sync_peer` loop: its receiver returns 422 for the new event kind, and a failed batch can block further replication.
4. If the rollout is only partially complete, keep peer traffic closed on every workstation. Take a fresh backup from each host and choose one code version for all three: either finish the reviewed upgrade everywhere or roll every host back and leave replication paused. Never sync a mixed set or restore one host's catalog over another's.
5. To resume replication, re-upgrade all three to the reviewed current release using the same per-host Database and replication catalogs. Verify all APIs/workers load that release and each peer handshake advertises `complex-review-annotation.v1`; then reopen the existing sync controls without cursor or epoch resets. Verify the saved decisions, rationales, conflict records and Evaluations on all three before reopening normal scientific work.

An older-version interval is therefore an offline replication interval. The log is retained as-is during downgrade and re-upgrade; the current version resumes from the existing per-peer cursors after all three hosts are compatible.
